## 一、API 陷阱（模块不存在 / 名称错误）

### 1.1 `$log` 不存在

```javascript
// ❌ 错误
$log("66600");  // 报错！$log 不存在

// ✅ 正确
log("66600");   // log 是全局函数，直接调用不加 $
```

**规则**：`log`、`sleep`、`tip`、`alert`、`toast`、`random`、`require`、`getClip`、`setClip` 属于 `$global` 全局函数，直接调用不加 `$`。

### 1.2 `$files` 不存在

```javascript
// ❌ 错误
$files.read(path);  // 报错！$files 不存在

// ✅ 正确
$file.read(path);   // 文件系统模块是 $file，不是 $files
```

### 1.3 `$ui.layout()` 路径错误

`$ui.layout()` 的路径相对于**项目根目录**（`project.json` 同级），不是相对于 JS 文件所在目录。

```javascript
// ❌ 错误
$ui.layout("xml/main.xml");      // 路径不对
$ui.layout("/main.xml");         // 不能用 / 开头

// ✅ 正确
$ui.layout("src/main.xml");      // 相对于项目根目录
```

### 1.3 `$dialog` 不在运行环境

```javascript
// ❌ 错误
$dialog.create(...);  // "找不到函数 create"

// ✅ 正确——使用 $floaty 或 $tip.show() 替代
// $dialog 是需要加载的 lib，不在默认运行环境里
```

### 1.4 `ui.ids()` 不存在

```javascript
// ❌ 错误
ui.ids("xxx");  // 报错

// ✅ 正确
ui.id("xxx");   // 单数形式，不是复数
```

### 1.5 `$floaty.create()` 不存在

```javascript
// ❌ 错误——链式调用全部失败
$floaty.create().setLayout().id().click().show();

// ✅ 正确——使用 new* 系列方法
$floaty.newApp(xml);
$floaty.newSys(xml);
$floaty.newAdj(xml);
```

### 1.6 全局函数不要加 `$` 前缀

```javascript
// ❌ 错误——以下函数都在 $global 中，直接调用
$sleep(1000);
$toast("提示");

// ✅ 正确
sleep(1000);
toast("提示");
```

## 二、XML 布局陷阱

### 2.1 `visibility="gone"` XML 属性不生效

```xml
<!-- ❌ 错误——visibility 在 XML 中不生效 -->
<frame id="hiddenLayer" visibility="gone" />
```

```javascript
// ✅ 正确——在 JS 中控制可见性
var ui = $ui.layout("main.xml");
ui.show();
ui.id("hiddenLayer").setVisibility($ui.GONE);
```

**原因**：AutoGOD XML 解析器不支持 `visibility` 属性，这是 Android 原生属性。

### 2.2 `gravity` vs `layout_gravity` 混淆

- `gravity` → 控制**自身内容**在自身范围内的对齐方式
  - 例：`<linear gravity="center">` 让 linear 内部的子控件居中排列
- `layout_gravity` → 控制**自身**在父布局中的位置
  - 例：`<frame layout_gravity="center">` 让 frame 在父布局中居中显示

**常见错误**：想让弹窗层居中显示，写了 `gravity="center"`，结果内容居中了但弹窗本身靠顶端对齐。

### 2.3 XML 根标签必须是 `<ui>`

```xml
<!-- ❌ 错误 -->
<?xml version="1.0"?>
<vertical>
</vertical>

<!-- ✅ 正确 -->
<ui>
    <linear dir="v">
    </linear>
</ui>
```

### 2.4 标签名必须小写

```xml
<!-- ❌ 错误 -->
<LinearLayout dir="v" />
<android.widget.LinearLayout dir="v" />

<!-- ✅ 正确 -->
<linear dir="v" />
```

### 2.5 属性名映射速查

| 错误写法 | 正确写法 |
|---------|---------|
| `orientation="vertical"` | `dir="v"` |
| `background="#FFF"` | `bg="#FFF"` |
| `textColor="#333"` | `color="#333"` |
| `layout_width="match_parent"` | `w="max"` |
| `layout_height="wrap_content"` | `h="wrap"` |
| `padding="10 20"`（空格分隔） | `padding="10,20"`（逗号分隔） |
| `textSize="16sp"` | `textSize="16"`（无单位）或 `textSize="16dp"` |

### 2.6 ID 前缀在 XML 中不需要

```xml
<!-- ❌ 错误——XML 中不需要 @+id/ 前缀 -->
<button id="@+id/btn1" />

<!-- ✅ 正确 -->
<button id="btn1" />
```

### 2.7 弹窗层无法显示（重要！）

**问题**：frame 弹窗 `setVisibility($ui.VISIBLE)` 后不显示。
**原因**：缺少外层 frame 容器。
**解决**：必须将所有内容放在外层 frame 中。

```xml
<!-- ❌ 错误结构 -->
<ui>
    <linear id="main">主界面</linear>
    <frame id="dialog">弹窗</frame>
</ui>

<!-- ✅ 正确结构 -->
<ui>
    <frame w="max" h="max">
        <linear id="main">主界面</linear>
        <frame id="dialog" layout_gravity="center">弹窗</frame>
    </frame>
</ui>
```

## 三、常见运行时错误

### 3.1 `$ui.create()` 不存在

- **问题**：运行时提示"找不到函数 create"
- **解决**：使用 `$ui.layout()` 传入 XML 模板字符串

### 3.2 `$file.write()` 参数顺序

- **问题**：文件写入失败
- **解决**：参数顺序是 `$file.write(content, path)`——内容在前，路径在后

### 3.3 `mAppbar` 未找到控件

- **问题**：运行时提示"未找到控件:mAppbar"
- **解决**：在 XML 中添加 `<appbar id="mAppbar" w="max" />`

### 3.4 屏幕尺寸获取错误

```javascript
// ❌ 错误
$device.info.screen.width;

// ✅ 正确
$screen.getWidth();
```

### 3.5 悬浮窗错误用法

- **问题**：用 `frame` 作为弹窗只能在当前页面显示
- **解决**：使用 `$floaty.newSys(xmlString)` 创建真正的系统级悬浮窗

### 3.6 drop 下拉框没有 setSelect 方法

- **问题**：运行时提示"找不到函数 setSelect"
- **解决**：使用 `select="0"` 在 XML 中设置默认选中项

### 3.7 动态创建视图的错误方式

```javascript
// ❌ 错误
var view = $ui.create("text");

// ✅ 正确
var view = $ui.layout(`<ui><text id="t1" text="hello" /></ui>`).id("t1");
```

## 四、线程陷阱

### 4.1 `$tip.input` / `$tip.show` 的回调在后台线程执行

**现象**：在 `$tip.input()` 或 `$tip.show()` 的回调中调用了 AIGame 代理 API，结果崩溃：

```
java.lang.IllegalStateException: FAILED ASSERTION
  at dj.xc.<init>(SourceFile:69)
  at java.lang.reflect.Proxy.invoke(Proxy.java:1006)
  at $ProxyXX.xxx(Unknown Source)
  at java.lang.Thread.run(Thread.java:764)
```

**原因**：`$tip.input()` / `$tip.show()` 的**回调函数是在后台线程执行的**（日志可见 `TName=Thread-XXX`）。AIGame 的代理 API 内部有线程上下文断言，在非 UI 线程上调用会抛出 `FAILED ASSERTION`。

---

### 🔍 真实案例复盘：为什么隔了一个 `require()` 就炸了

#### 背景

海岛助手 app 的"生成存档"按钮，逻辑：

```
用户点击 → $tip.input 弹窗 → 用户输入名称点确定 → 回调 → 导出存档
```

#### 崩溃现场

```
 D  17:21:03 用户取消导出账号存档
 D  17:21:09 开始导出账号存档: 123
 E  17:21:09 全局异常:TID=530TName=Thread-175
    java.lang.IllegalStateException: FAILED ASSERTION
      at dj.xc.<init>(SourceFile:69)
      at java.lang.reflect.Proxy.invoke(Proxy.java:1006)
      at $Proxy14.value(Unknown Source)
      at java.lang.Thread.run(Thread.java:764)
```

关键信息：线程名 `Thread-175` + `$Proxy14.value`。

#### 排查过程

沿着调用链往回追：

```
$tip.input 回调（Thread-175）
  → accountManager.exportAccountArchive("123")
    → copy_shell()
      → getGamePackageName()
        → require("./configManager.js")   ← 已缓存，不触发 I/O
        → configManager.loadConfig()      ← 内部调 $file.read()
          → $Proxy14.value               ← 💥 断言失败
```

**注意这里的陷阱**：`configManager.js` 虽然在 `main.js` 顶部已经加载过了（`let configManager = require("./modules/configManager.js")`），所以 `getGamePackageName()` 里第二次 `require()` 返回的是缓存，**不会触发 I/O**。真正导致崩溃的是 `configManager.loadConfig()` 内部调用的 `$file.read()`。

但如果 `getGamePackageName()` 里 `require()` 的是一个**还没加载过**的模块，那 `require()` 本身的文件 I/O 也会触发同样的断言崩溃。

**对比两个版本的 `getGamePackageName()`：**

| 版本 | 代码 | 走代理？ |
|------|------|---------|
| **aigame版（能工作）** | `ui.id("serverType").getText()` | ❌ 纯 Java getter |
| **当前版（崩溃）** | `configManager.loadConfig()` — 内部调 `$file.read()` | ✅ `$file.*` 走代理 |

`ui.id("serverType").getText()` **不走 AIGame 动态代理**，只是一个普通的 Java getter，所以在后台线程上也能安全调用。而 `configManager.loadConfig()` 内部调 `$file.read()` → 触发 AIGame 动态代理 → 代理构造函数的线程断言检查发现当前是 `Thread-175`（不是合法线程）→ `FAILED ASSERTION`。

> ⚠️ **重要细节**：`configManager.js` 在 `main.js` 顶部已经被 `require()` 加载过，所以 `getGamePackageName()` 里第二次 `require("./configManager.js")` 返回的是**缓存模块**，不会触发文件 I/O。真正触发代理断言的是 `loadConfig()` 内部调用的 `$file.read()`。如果 `require()` 的是一个还没加载过的模块，那 `require()` 本身的文件 I/O 也会触发同样的崩溃——两种都要警惕。

#### 修复

把 `getGamePackageName()` 从读配置文件改为直接读 UI 控件：

```javascript
// ❌ 原来：读配置文件，触发代理
function getGamePackageName() {
    let configManager = require("./configManager.js");
    let config = configManager.loadConfig();
    let serverTypeText = config.serverType || "国际服";
    // ...
}

// ✅ 修复后：直接读 UI 控件，纯 Java getter
function getGamePackageName() {
    let serverTypeText = ui.id("serverType").getText();
    // ...
}
```

#### 这个案例的教训

崩溃栈 `$Proxy14.value` + `Thread-XXX` 指向的是"某个 AIGame 代理 API 在后台线程被调用了"，但**具体是哪个 API**不一定在崩溃栈里直接显示——`$Proxy14` 只是 AIGame 内部动态代理的编号。需要沿着调用链回溯，找出哪个函数触发了 `$file.*` 等操作。很多时候 bug 就藏在 `loadConfig()` 这种看起来人畜无害的调用里，抓住**线程名**+**代理调用**两个特征就可以快速定位。

> 注意 `require()` 的缓存行为：已加载过的模块不会触发 I/O，但首次加载某个模块时也会触发代理断言。

---

### 会触发断言的操作清单

- `$file.read()` / `$file.write()` / `$file.join()` / `$file.exists()` 等所有 `$file.*` ❌
- `$storage.*` ❌
- `require("未加载的模块")` — 首次加载触发文件 I/O ❌
- `configManager.loadConfig()` — 内部调用 `$file.*` ❌

### 不会触发断言的操作清单

- `$root.exeRootShell()` — 不走 `$file`/`$storage` 的代理，实测在后台线程安全 ✅
- `require("已加载的模块")` — 返回缓存，不走 I/O ✅
- `ui.id("xxx").getText()` — 纯 Java getter ✅
- `ui.id("xxx").getCheckedText()` ✅
- `toast()` / `$log.*` ✅
- 纯 JS 逻辑（字符串拼接、JSON.parse 等）✅

> ⚠️ **注意**：断言是**按代理模块分别实现的**，不是所有 AIGame API 都有线程断言。`$file.*` 和 `$storage.*` 有，`$root.exeRootShell()` 没有。不能一刀切认为所有 AIGame API 都不安全。

### ✅ 正确写法

```javascript
// 方案1：模块先在 UI 线程加载好，回调只调用函数（不触发 require）
let accountManager = require("./modules/accountManager.js"); // UI 线程加载

$tip.input("导出存档", "请输入名称", "", function (result) {
    if (result) {
        accountManager.exportArchive(result); // 安全：不触发 require
    }
});

// 方案2：用 UI 控件属性代替读配置（纯 getter 不走代理）
function getGamePackageName() {
    let text = ui.id("serverType").getText(); // ✅ 安全
}
```

### 如何排查

1. 看崩溃日志的线程名是不是 `Thread-XXX`（不是 `main`）
2. 看堆栈有没有 `$ProxyXX.xxx` 字样（AIGame 动态代理调用）
3. 回溯代码，从崩溃点沿着调用链往外走，找出哪个函数在后台线程上调了 `$file.*`、`$storage.*` 等 API
4. 特别留意 `$file.*` 调用——即使藏在 `loadConfig()` 这种看似无害的函数内部，也会触发代理断言
5. `$root.exeRootShell()` 是安全的，不需要怀疑它

### 4.2 💥 终极版：$root.exeRootShell 回调 + $file.* = 怎么绕都会 FAILED ASSERTION

**现象**：在 `$root.exeRootShell()` 的回调中读写文件，试了 3 种方案都崩溃：

| 尝试 | 代码 | 崩溃栈 | 线程 |
|------|------|--------|------|
| 直接调 `$file.*` | `$file.write(...)` | `$Proxy13.complete` | `Thread-45` |
| 用 `$ui.run()` 包裹 | `$ui.run(() => $file.write(...))` | `$Proxy4.run` / Handler | `main` |
| 用 `setTimeout(0)` 包裹 | `setTimeout(() => $file.write(...), 0)` | `$Proxy5.run` | `Thread-45` |

**崩溃栈（第三次）**：
```
E  全局异常:TID=246TName=Thread-45
   java.lang.IllegalStateException: FAILED ASSERTION
     at dj.xc.<init>(SourceFile:69)
     at java.lang.reflect.Proxy.invoke(Proxy.java:1006)
     at $Proxy5.run(Unknown Source)
     at java.lang.Thread.run(Thread.java:764)
```

**为什么 `$ui.run()` 和 `setTimeout()` 也不行**？
- `$ui.run(Runnable)` 内部通过 Handler 将 Runnable 抛到主线程，但 Runnable 被 AIGame 动态代理包裹（`$Proxy4.run`），代理构造函数有线程断言，**即便在主线程也报错**
- `setTimeout(fn, 0)` 从后台线程调用时，回调在 AIGame 的**定时器线程**执行，同样被 `$Proxy5` 代理包裹

**根本原因**：AIGame 给 `$file.*`、`$storage.*`、`$ui.run()`、首次 `require()`、甚至定时器回调都加了动态代理。这些代理内部**硬编码了允许的线程列表**（可能只有主线程和脚本引擎线程）。任何其他线程调用都会触发 `FAILED ASSERTION`。

**✅ 最终方案：Java File API**

在后台线程读写文件，不要用 `$file.*`，直接用 **Java 原生 File API**（不走 AIGame 代理系统）：

```javascript
// 写文件（后台线程安全）
var fos = new java.io.FileOutputStream(path);
fos.write(new java.lang.String(content).getBytes("UTF-8"));
fos.close();

// 读文件（后台线程安全）
var fis = new java.io.FileInputStream(path);
var bytes = java.lang.reflect.Array.newInstance(java.lang.Byte.TYPE, fis.available());
fis.read(bytes);
fis.close();
var content = new java.lang.String(bytes, "UTF-8");

// 删除目录（后台线程安全）
var file = new java.io.File(dirPath);
var files = file.listFiles();
if (files) {
    for (var i = 0; i < files.length; i++) {
        files[i].delete();
    }
}
file.delete();
```

**完整清单——后台线程能用 vs 不能用：**

| ❌ 不能用（FAILED ASSERTION） | ✅ 能用 |
|---|---|
| `$file.read/write/exists/join/mkdir/removeDir` | `$root.exeRootShell()` |
| `$storage.*` | `$log.*`、`toast()` |
| `require("未加载的模块")`（首次加载走 I/O） | `require("已加载的模块")`（缓存，不走 I/O） |
| `$ui.run(fn)` | `ui.id("xxx").getText()`（纯 Java getter） |
| `setTimeout(fn, 0)`（从后台线程调用） | Java File API（`java.io.*`） |
| `$file.ensureDir(dir)` | 纯 JS 逻辑 |

> **规律**：任何方法名中带 `$` 的基本都是 AIGame 动态代理 API，在后台线程大概率不安全。Java 原生 API 和纯 JS 是安全的。

### 4.3 ⚠️ require() 多次执行模块：const/let 重新声明

**现象**：在 `$tip.input` 的回调（后台线程）或 `setInterval` 等上下文中调 `require("accountStorage.js")`，报错：

```
E  刷新账号列表失败: 类型错误：重新声明了常量 CACHE_TTL
```

**原因**：AIGame 的 `require()` 虽然**缓存导出值**（多次 require 返回同一个对象），但每次调用时**依然会重新执行模块的脚本体**。如果模块顶层有 `const` 声明，第二次 require 时就会报重复声明错误。`let` 在非严格模式下允许重复声明，所以没问题。

```javascript
// accountStorage.js — ❌ const 会报错
const STORAGE_VERSION = 1;    // 第二次 require() → 重新声明常量
const STORAGE_FILE_NAME = "accounts.json";

// ✅ let 在非严格模式下允许重复声明，没问题
let CACHE_TTL = 10000;
let _cache = null;

// ✅ var 也可以
var STORAGE_VERSION = 1;
var STORAGE_FILE_NAME = "accounts.json";
```

**注意**：`var` 重复声明虽然不会报错，但每次 `require()` 都会重复执行赋值语句。如果赋值开销较大或有副作用，建议用**模块级初始化标志**来防护：

```javascript
var _initialized = false;
if (!_initialized) {
    _initialized = true;
    // 只执行一次的初始化逻辑
}
```

> ⚠️ AIGame 的 `require()` 行为与 Node.js 不同：Node.js 的 `require()` 缓存**整个模块的导出**且只执行一次脚本体；AIGame 的 `require()` 缓存**导出对象**但**每次重新执行脚本体**。

### 🔍 真实案例复盘2：怎么绕都绕不过的 $root.exeRootShell 回调 + JSON 存档导出

#### 背景

海岛助手 app 的"生成存档"功能，原先是 root shell `cp` 复制文件到子目录。改造成 JSON 存储引擎后，需要在 `$root.exeRootShell()` 的回调中读取 XML 内容、写入 `accounts.json`，结果遭遇了最顽强的 `FAILED ASSERTION`——绕了 4 次才解决。

#### 完整演化过程

| # | 方案 | 崩溃 | 代码 |
|---|------|------|------|
| 1 | 直接在回调中 `require + $file` | `$Proxy13.complete` | `readStorageContent` 回调 → `require("./accountStorage.js")` → `$file.write(accounts.json)` |
| 2 | 用 `$ui.run()` 包裹 | `$Proxy4.run` via Handler | `$ui.run(() => { require + $file })` |
| 3 | 用 `setTimeout(0)` 包裹 | `$Proxy5.run` via Thread | `setTimeout(() => { require + $file }, 0)` |
| 4 | 纯 Java File API | ✅ 成功 | `new java.io.FileOutputStream(path)` |

#### 崩溃链 1：$tip.input 弹窗（Thread-175）

```
用户点击"生成存档"→ $tip.input 弹窗
  → 用户输入名称点确定 → $tip.input 回调（Thread-175）
    → getGamePackageName()
      → configManager.loadConfig()     ← 内部调 $file.read()
        → 💥 $Proxy14.value
```

修复：把 `getGamePackageName()` 从读配置文件改为读 UI 控件。

#### 崩溃链 2：国际服自动存档（Thread-45）

```
用户点击"生成存档"（国际服自动）
  → getAccountNameFromGame()
    → $root.exeRootShell(cat ...) 回调（Thread-45）
      → exportAccountArchiveJSON()
        → readStorageContent()
          → $root.exeRootShell(cat ...) 回调（Thread-45）
            → _saveExportToJSON()
              → require("./accountStorage.js")     ← 💥 首次加载走 I/O
                → 💥 $Proxy13.complete
```

第一次修：`$ui.run()` 包裹 → 💥 `$Proxy4.run`
第二次修：`setTimeout(0)` 包裹 → 💥 `$Proxy5.run`
最终修：**Java File API**（`java.io.*`）— 不走 AIGame 代理

#### 崩溃链 3：列表刷新时的 const 重声明

```
setInterval（UI 线程）
  → refreshAccountList()
    → require("./accountStorage.js")   ← 模块已加载过，但重新执行脚本体
      → const CACHE_TTL = 10000         ← 💥 重声明常量
```

修复：模块顶层的 `const` / `let` 改为 `var`。

#### 这个案例的教训

1. **`$root.exeRootShell()` 回调 = 后台线程**。在里面做任何 `$file.*`、首次 `require()` 都会 FAILED ASSERTION
2. **`$ui.run()` 和 `setTimeout(0)` 也会炸**。AIGame 给这些"接力"API 也加了代理
3. **最终方案：Java File API**。`java.io.FileOutputStream`、`java.io.FileInputStream` 不走代理，后台线程随便用
4. **`require()` 会重新执行脚本**。模块顶层的 `const`/`let` 第二次就被重声明

### 5.3 运行时错误速查

| 报错信息 | 原因 | 解决 |
|---------|------|------|
| `找不到函数 create` | 调用了不存在的 API | 查文档确认正确的 API 名 |

| `TypeError: xxx is not a function` | API 名写错或不存在 | 核对文档确认 API 签名 |

### 5.4 线程相关（FAILED ASSERTION）完整速查

**判断方法**：崩溃日志中同时出现：
- `TName=Thread-XXX`（不是 `main`）或 `$ProxyXX.xxx`
- `java.lang.IllegalStateException: FAILED ASSERTION`

**哪些后台线程会触发？**

| 来源 | 线程 | 典型回调 |
|------|------|---------|
| `$tip.input/show` 弹窗确定 | `Thread-XXX` | 用户点击确定后的回调 |
| `$root.exeRootShell()` | `Thread-XXX` | exitCode 回调 |
| `setTimeout(fn, 0)`（从后台线程调用） | `Thread-XXX` | 定时器回调 |
| `$ui.run(fn)` | `main`（但经代理包裹） | Runnable 的 run |

**✅ 后台线程安全的操作：**

```
$root.exeRootShell()
$log.*
toast()
ui.id("xxx").getText()          ← 纯 Java getter
ui.id("xxx").getCheckedText()    ← 纯 Java getter
require("已加载过的模块")         ← 返回缓存
Java File API (java.io.*)        ← 不走 AIGame 代理
纯 JS 逻辑（JSON.parse、Math、字符串拼接等）
```

**❌ 后台线程会崩溃的操作：**

```
$file.read/write/exists/join/mkdir/removeDir/ensureDir
$storage.put/get/remove
require("还没加载过的模块")      ← 首次加载走 I/O
$ui.run(fn)                     ← Runnable 被代理包裹
setTimeout(fn, 0)               ← 定时器线程也被代理包裹
configManager.loadConfig()      ← 内部调 $file.read()
任何以 $ 开头的 API             ← 大概率走代理
```

**万能口诀：后台线程想读写文件，用 Java File API，别碰 `$file.*`！**

### 5.5 模块系统（require）注意事项

| 特性 | Node.js | AIGame |
|------|---------|--------|
| **导出值缓存** | ✅ 缓存 | ✅ 缓存 |
| **脚本执行次数** | 首次 require 执行一次 | **每次 require 都重新执行** |
| **模块顶层 const** | 安全 | ❌ 第二次 require 报重声明 |
| **模块顶层 var** | var 的赋值语句 | 每次重新赋值但不会报错 |

**结论**：
- 模块顶层声明 → 用 `var`
- 需要只执行一次的初始化 → 加 `_initialized` 标志
- 不要在后台线程首次 `require()` 未加载的模块

### 5.6 避坑黄金法则

1. **`$` 前缀 = 代理 API** → 后台线程大概率不安全
2. **用 Java File API 代替 `$file.*`** 在后台线程读写文件
3. **模块顶层用 `var` 或 `let`**，别用 `const`（AIGame require 重新执行脚本，const 不允许多次声明）
4. **UI 控件属性**（`getText()`）是纯 Java getter，后台线程安全
5. **`$root.exeRootShell()` 是安全的**，但它的回调在后台线程
6. **XML 不是 Android XML**，标签小写、属性用缩写、根节点 `<ui>`
7. **`<ls>` 列表用 `bindHolder` + `flush`**，不是 `itemClick`/`setDataSource`
8. **遇到 FAILED ASSERTION** → 找 `Thread-XXX` + `$ProxyXX` → 回溯哪个 API 在后台线程被调用

### 5.7 跨线程通信：JS 变量不可见，用文件系统

**现象**：后台线程（`$root.exeRootShell`/`$tip.input` 回调）中数据操作成功后，UI 不刷新。重启应用后数据正确。

**根因**：AIGame 的 JavaScript 引擎在**不同线程上使用独立的 JS 作用域**。后台线程设置的 `var flag = true`，主线程的 `setInterval` 看不到。同理 `Handler.post()` 的 Runnable 虽然跑在主线程 Handler，但引用的 JS 变量在后台线程作用域定义——两个作用域不互通。

**尝试过的方案（全部失败）：**

| 方案 | 结果 | 原因 |
|------|------|------|
| 全局变量 + `setInterval` 轮询 | ❌ | 前后台 JS 作用域隔离，变量不可见 |
| `setInterval` 从 UI 线程 click 回调启动 | ❌ | 回调在定时器线程执行，AIGame API 静默失败 |
| `Handler.getMainLooper().post()` | ❌ | Runnable 在主线程 Handler 执行，但引用的 JS 变量在后台线程作用域 |

**最终方案（标记文件）：**

后台线程用 Java File API 写标记文件 → 主线程 `setInterval` 检测标记文件 → 刷新 UI。

```javascript
// 后台线程：数据操作成功后写标记文件（Java File API，任何线程安全）
function _markPendingRefresh() {
    var flag = new java.io.File(context.getExternalFilesDir(null), ".pending_refresh");
    flag.createNewFile();
}

// 主线程：定时检测标记文件（setInterval 从顶层级启动，回调在主线程执行）
setInterval(function () {
    var flag = new java.io.File(context.getExternalFilesDir(null), ".pending_refresh");
    if (flag.exists()) {
        flag["delete"]();
        refreshAccountList(); // AIGame API 安全
    }
}, 800);
```

**避坑要点：**
- ❌ 不要依赖 JS 变量做跨线程通信（作用域隔离）
- ❌ 不要从后台线程的回调中调 `setTimeout`/`setInterval`（定时器线程不安全）
- ❌ `Handler.post()` 的 Runnable 跑在主线程但 JS 变量在后台线程作用域
- ✅ 用 Java File API 写标记文件做跨线程通信
- ✅ `setTimeout`/`setInterval` 在顶层级（`$ui.layout()` 后）启动，回调在主线程安全

### 🔍 真实案例复盘4：回调永不执行——callback = null 放在了条件判断之前

#### 背景

海岛助手 app 的上号（切换存档）功能：`writeStorageContent()` 先用 `$root.exeRootShell` 写第 1 个文件（storage.xml），国际服还要写第 2 个（storage_new.xml）。两个文件的退出回调都会调用 `tryFinish()` 判断是否全部完成。

#### 现象

```
I  storage.xml 写入成功
I  storage_new.xml 写入成功
D  临时目录已清理
                                                    ← 没有 "上号成功" toast
                                                    ← 没有启动游戏
```

存档写入成功了，但成功的回调函数没有被执行。文件的 `cp` 操作一切正常，`tryFinish()` 也被调用了，但传给调用者的 `callback` 没有被触发。

#### 崩溃现场

```javascript
function tryFinish() {
    var _callback = callback;
    callback = null; // ← 💥 防重复调用
    var _ok = result.xml1 && result.xml2 && !hasError;
    if (result.xml1 && result.xml2 || hasError) {
        _javaDeleteDir(_tempDir);
        if (_callback) _callback(_ok);
    }
}
```

#### 根因

`tryFinish()` 被设计为同时处理两个文件的完成状态：

1. **第 1 个文件完成**（storage.xml）：`result.xml1 = true`，但 `result.xml2` 还是 `false`
   - 条件 `true && false || false` = `false` → 不进入 `if` 块
   - **但是 `callback = null` 已经被执行了！** ← 💥

2. **第 2 个文件完成**（storage_new.xml）：`result.xml2 = true`
   - `var _callback = callback` → `_callback = null`（因为上一步已经置空了）
   - `if (_callback)` → `false` → **回调永远不会执行**

#### 执行流程

```
第1个文件完成 → tryFinish()
  → var _callback = callback  // 保存回调
  → callback = null            // 置空 ← 💥 这一步不应该在这里
  → 条件不满足 → 不执行回调    // 正常
  → 函数结束

第2个文件完成 → tryFinish()
  → var _callback = callback  // 已经 null 了！
  → 条件满足
  → if (_callback) → false    // ← 💥 永远不会执行
```

#### 修复

将 `callback = null` **移到 `if` 块内部**，仅在真正需要调用回调时才置空：

```javascript
function tryFinish() {
    var _ok = result.xml1 && result.xml2 && !hasError;
    if (result.xml1 && result.xml2 || hasError) {
        var _cb = callback;
        callback = null; // ✅ 仅在调用回调前防重
        _javaDeleteDir(_tempDir);
        if (_cb) _cb(_ok);
    }
    // ❌ 条件不满足时，callback 保持原值，下次还能用
}
```

#### 教训

1. **防御性代码不能放在防御目标之前**。`callback = null` 的目的是防止 `tryFinish` 被重复调用时回调被执行两次。但如果把它放在条件判断之前，即使条件不满足也会执行置空，导致后续条件满足时回调已丢失。

2. **多文件异步完成模式**：当多个 root shell 操作需要全部完成后触发回调时，正确的模式是：
   - 维护 `completed` 计数器
   - 每次回调时递增计数器
   - 仅当 `completed === total` 时才调用最终回调

   ```javascript
   var completed = 0;
   var total = 2;
   
   function tryFinish() {
       completed++;
       if (completed === total) {
           _javaDeleteDir(tempDir);
           callback(true); // 仅最后一次调用时触发
           callback = null;
       }
   }
   ```

3. **防重复调用的 guard 必须紧挨着被保护的调用**，放在条件判断内部。

4. **定位技巧**：当 "数据操作成功但回调没执行" 时，先检查防重复调用的 guard 是否放错了位置——这是很隐蔽的 bug。

## 六、脚本执行与停止陷阱

### 6.1 用 `$engine.run()` 而非 `require().run()` 启动脚本

**问题：** 用 `require("./scripts/xxx.js")` + `script.run()` 启动脚本，脚本在主线程运行，点击停止时无法被终止。

```javascript
// ❌ 错误 — 无法停止
let script = require("./scripts/myScript.js");
script.run();

// ✅ 正确 — 可被 $engine.stopAll() 停止
$engine.run("./scripts/myScript.js");
```

**脚本文件**（`scripts/xxx.js`）不要包 `run()` 函数，直接写顶层逻辑：

```javascript
// ✅ 正确：直接写顶层
let floatys = require("../modules/floatyLog.js");
floatys.show();
// ... 主逻辑直接放在顶层 ...

// ❌ 错误：包一层 run() 导出给谁用？
function run() { ... }
let api = { run: run };
module.exports = api;
```

**停止脚本：**
```javascript
$engine.stopAll();  // 终止所有引擎任务
$thread.stopAll();  // 终止所有线程（后备）
```

### 6.2 SysFloaty 窗口单例模式

多处 `require("floatyLog.js")` 会创建多个窗口实例。用 `global` 对象共享状态：

```javascript
var G = typeof global !== "undefined" ? global : (function(){return this;})();
if (typeof G.__mySingleton === "undefined") {
    G.__mySingleton = { win: null, ... };
}
var S = G.__mySingleton;
```

注意：AutoGOD 中 `global` 可能未定义，用 `(function(){return this;})()` 兜底获取全局对象。

## 七、原生操作技巧（getView）

### 7.1 用 getView() 获取原生 Android 控件

AIGame 的控件（`XView`）可以通过 `.getView()` 获取对应的**原生 Android View 对象**，然后直接调用 Android SDK API。这在 AIGame 的 XML 属性或 Style 不生效时特别有用。

```javascript
// 获取原生 View
let myBtn = ui.id("myButton");
let nativeView = myBtn.getView();  // MaterialButton 对象
```

**控件 -> 原生类对照表：**

| AIGame 标签 | 原生类 |
|------------|--------|
| `<button>` | `com.google.android.material.button.MaterialButton` |
| `<text>` | `com.google.android.material.textview.MaterialTextView` |
| `<input>` | `com.google.android.material.textfield.TextInputLayout`（内部含 `TextInputEditText`，通过 `.getEditText()` 获取） |
| `<card>` | `com.google.android.material.card.MaterialCardView` |
| `<switch>` | `com.google.android.material.switchmaterial.SwitchMaterial` |

> ⚠️ `getView()` 返回的是安卓原生对象，在 **UI 线程**中操作是安全的。AIGame 封装过的 `setText()` 等可以自动跨线程，但原生 API 需要在 UI 线程调用或在 `bindHolder` 等已知 UI 上下文中使用。

### 7.2 实际案例：列表内按钮 XML 样式不生效

**现象**：`<ls>` 列表模板中的 `<button>` 设置了 `bg`、`textColor`、`style` 等属性，但预览时按钮是空白、文字不显示。

**原因**：在 `<ls>` 的 `<layout>` 子项模板中，AIGame 的部分 XML 样式属性可能不会正确解析。这是 AIGame 对 RecyclerView 内部的 View 渲染方式的限制。

**解决**：在 `bindHolder` 回调中调用 `getView()`，用 Android 原生 API 直接设置样式。

```javascript
AccountList.bindHolder(function (itemUi, itemData, position) {
    let loadBtn = itemUi.id("loadArchive");
    if (loadBtn) {
        var btn = loadBtn.getView();
        btn.setText("加载");
        btn.setTextSize(12);
        btn.setBackgroundColor(android.graphics.Color.parseColor("#4CAF50"));
        btn.setTextColor(android.graphics.Color.parseColor("#FFFFFF"));
        btn.setPadding(12, 4, 12, 4);
        loadBtn.click(function () { });
    }
});
```

**完整思路：** 列表模板只定义结构，样式全部在 `bindHolder` 中用原生 API 设置。

### 7.5 实际案例：Card 内边距太大（下巴）

**现象**：`<card>` 内容垂直方向有大量空白，"下巴"很重。

**原因**：`MaterialCardView` 有默认的阴影内边距（8-12dp），XML 中设 `padding="0"` 无效。

**解决**：
```javascript
itemUi.id("cardRoot").getView().setContentPadding(8, 2, 8, 2);

```

**`MaterialCardView` 常用原生 API**：

| 方法 | 说明 |
|------|------|
| `setContentPadding(l, t, r, b)` | 设置内容内边距 |
| `setCardElevation(float)` | 设置阴影高度，0 为无阴影 |
| `setRadius(float)` | 设置圆角半径 |
| `setCardBackgroundColor(color)` | 设置背景色 |

**注意事项：**
1. **调用时机**：`getView()` 需在 UI 渲染完成后调用，`setTimeout` 或事件回调中安全。
2. **线程安全**：原生 Android View 操作**必须在 UI 线程**。
3. **控件生命周期**：原生引用在控件存续期间有效，销毁后不要继续持有。
4. **优先用 AIGame 封装**：`setText`、`setEnabled`、`setVisibility`、`click` 等 AIGame 已有封装，优先使用。只在 XML 样式不生效时用原生 API。

## 八、Android 12+ Root 权限与 mount namespace 问题

### 8.1 现象

在 Android 12+ 设备（尤其是 ColorOS / 真我 / OPPO）上，以下操作在模拟器上正常，但在真机上失效：

- `$root.exeRootShell("cat /data/user/0/包名/...")` → 返回退出码 1，提示文件不存在
- `$root.exeRootShell("ls /data/user/0/")` → 只能看到本应用和 Google 服务，看不到其他应用
- 但用 MT 管理器或 ADB shell 有 root 权限时可以正常访问

**原因：Android 12+ 的 mount namespace 隔离**

从 Android 12 开始（尤其是 ColorOS 13），Magisk/SuperSU 的 `su` 命令在向非特权应用授予 root shell 时，默认创建一个**隔离的 mount namespace**。在这个隔离空间里，其他应用的数据目录（`/data/user/0/`）被隐藏，只能看到本应用自己的目录。

**关键区别：**

| 环境 | 能否访问 `/data/user/0/其他应用` | 原因 |
|------|------|------|
| 模拟器 | ✅ 可以 | 模拟器没有 mount namespace 隔离 |
| MT 管理器 | ✅ 可以 | MT 向 Magisk 请求了全局 namespace |
| AIGame `$root.exeRootShell` | ❌ 不行 | 默认使用隔离 namespace |
| ADB shell `su` | ✅ 可以 | 从 ADB 获取的 root 是全局的 |

### 8.2 解决方案：使用 `nsenter` 进入全局 mount namespace

```javascript
// ❌ 错误：在隔离 namespace 中，看不到其他应用的数据
$root.exeRootShell("cat /data/user/0/com.supercell.boombeach/shared_prefs/storage.xml",
    ...  // 返回 exitCode=1, "No such file or directory"
);

// ✅ 正确：用 nsenter 进入 init 进程的 mount namespace
$root.exeRootShell(`nsenter -t 1 -m -- cat /data/user/0/com.supercell.boombeach/shared_prefs/storage.xml`,
    ...  // 正常读取
);
```

**原理：** `nsenter -t 1 -m` 进入 PID 1（init 进程）的 mount namespace，这个 namespace 有完整的全局挂载视图，可以看到所有应用的数据目录。

### 8.3 必须使用 nsenter 的场景

所有通过 `$root.exeRootShell` 执行的、需要访问**其他应用数据目录**的命令，都必须加 `nsenter -t 1 -m --` 前缀：

| 命令类型 | 示例 | 需要 nsenter |
|---------|------|------------|
| 读取游戏存档 | `cat /data/user/0/.../storage.xml` | ✅ 必须 |
| 写入游戏存档 | `cp /tmp/storage.xml /data/user/0/.../` | ✅ 必须 |
| 检查文件存在 | `test -e /data/user/0/.../fingerprint.json` | ✅ 建议（部分设备无需） |
| 执行锁云脚本 | `sh /path/to/lock.sh`（脚本内访问 `/data/user/0/`） | ✅ 必须 |
| 删除应用数据 | `rm -rf /data/user/0/.../update` | ✅ 必须 |
| 修改文件权限 | `chmod -R 777 /data/user/0/.../update` | ✅ 必须 |
| 本应用自身目录 | `cat /data/user/0/org.auto.god/...` | ❌ 不需要 |
| `/sdcard/` 目录 | `ls /sdcard/` | ❌ 不需要 |

### 8.4 注意事项

1. **nsenter 可用性：** 所有 Android 系统都有 `nsenter`（属于 toybox），无需额外安装。

2. **`--` 分隔符：** nsenter 的参数和要执行的命令之间必须加 `--`：
   ```javascript
   // ✅ 正确
   nsenter -t 1 -m -- cat /path/to/file
   // ❌ 错误（-c 被当作 nsenter 的参数）
   nsenter -t 1 -m sh -c "cmd"
   ```

3. **传参引用：** 路径中有特殊字符（如括号、空格）时，必须在 nsenter 内部引用：
   ```javascript
   // ✅ 正确：外层用模板字符串，内部用单引号
   `nsenter -t 1 -m -- sh -c 'cd "${path}" && sh "${script}"'`
   ```

4. **`$root.getPermit()` 必须调用：** 在真机上，`$root.hasPermit()` 返回 true 不保证 root shell 可用，必须先调用 `$root.getPermit()` 打开 root 会话：
   ```javascript
   $root.getPermit();  // 阻塞等待 root shell 打开
   $root.exeRootShell(`nsenter -t 1 -m -- cat ...`);
   ```

5. **ColorOS `am force-stop` 兼容性：** 真我/OPPO 的 ColorOS 上 `am force-stop` 会报 NullPointerException（系统 Bug），不会阻断命令执行，但 `&&` 链会被打断。建议用 `;` 代替 `&&`：
   ```javascript
   // ✅ ColorOS 安全
   "cmd1; am force-stop pkg 2>/dev/null; echo 完成"
   // ❌ force-stop 失败会阻断后续命令
   "cmd1 && am force-stop pkg && echo 完成"
   ```

### 8.5 完整案例：锁云/解锁封装

参见 `modules/lockcloud.js` 中的 `performLockCloud` 和 `performUnlockCloud` 函数，核心模式：

```javascript
// 1. 获取 root shell
$root.getPermit();

// 2. 所有操作通过 nsenter 进入全局 namespace
$root.exeRootShell(`nsenter -t 1 -m -- sh -c 'rm -rf /data/user/0/包名/update'`,
    (line) => { /* stdout */ },
    (err) => { /* 错误 */ },
    (exitCode) => { /* 完成 */ }
);
```

### 8.6 如何避免此类问题

1. **开发时用真机测试：** 模拟器没有 mount namespace 隔离，所有 root 操作在模拟器上都能跑通。必须在 Android 12+ 真机上验证 root 相关功能。

2. **测试 `/data/user/0/` 可见性：** 在真机上运行以下代码，如果只看到 2-3 个包名，说明有 namespace 隔离：
   ```javascript
   $root.exeRootShell("ls /data/user/0/",
       line => $log.i("包名: " + line),
       null,
       code => $log.i("退出码: " + code)
   );
   ```

3. **所有涉及其他应用数据目录的 root 命令，一律加 `nsenter -t 1 -m --` fallback：** 养成习惯，不加思考。但部分模拟器没有 `nsenter`，必须用 `||` fallback 同时兼容两边：

   ```javascript
   // ✅ 真机 + 模拟器都兼容
   `nsenter -t 1 -m -- cat /data/user/0/包名/file 2>/dev/null || cat /data/user/0/包名/file`
   ```
   原理：`nsenter` 不存在时返回退出码 127，`||` 触发 fallback 执行普通命令。

4. **优先使用 `$screen.info()` 获取屏幕数据：** `$screen.getWidth()` 可能返回去导航栏后的可用宽度，`info.w` 返回物理全屏宽度，更可靠。dp→px 公式：`1dp = dpi / 160 (px)`。

### 9.6 `button-group` 布局时会自动触发一次 `onCheck(0)`

**现象**：用 `button-group` 做二选一，在 `onCheck` 里写配置。每次启动 App，配置都会**先被写成第 0 项、再改回上次的值** —— 中途崩了就丢配置。

**原因**：`button-group` 在布局时会自己触发一次 `onCheck(0)`（`selectRequire` 强制有选中项），
而恢复上次选择时调的 `check(idx)` **也会再触发一次**。

**解决**：加一道「初始化完成」闸

```javascript
let ready = false;
group.onCheck((index) => {
    if (ready) { configManager.updateConfig("xxx", names[index]); }   // 只有用户真实切换才写
});
// ...读取并恢复上次选择...
group.check(savedIndex);
ready = true;
```

**另外**：`button-group` **没有** `getCheckedIndex()` / `getCheckedText()`（那是 `radio-group` 才有的），
选中值**必须自己用变量记住**。

### 9.7 `button-group` 没有 `color` / `radius` 属性

`<button-group>` 的属性**只有**：`dir` / `bg` / `bgImg` / `singleSelect` / `selectRequire` / `padding` / `gravity`
方法只有：`check(index)` / `onCheck(callback)`

`color`（主题颜色）和 `radius`（弧度）是 **`<button>` 的**属性。写在 `<button-group>` 上**不报错，但也不生效**。

**另一个实测**：给 `style="outline"` 的 button 加 `color`，会让**组内所有按钮都变成实心同色**，
反而分不出哪个选中 —— **不要自己加颜色**，交给主题和 `style` 走。

**参考**：官方现成示例在 `examples/$ui - 交互界面/03.button-group-按钮组/`，照它写最稳。

### 9.8 `$engine.run("./scripts/x.js")` 的工作目录会变成 `scripts/`

**现象**：脚本里写 `./res/lib/xxx.dex` 找不到，日志报：

```

```

**原因**：用 `$engine.run("./scripts/x.js")` 启动的脚本，**工作目录是 `scripts/`，不是项目根目录**，
所以 `./res/...` 被解析成了 `./scripts/res/...`。

**解决（三选一）**：
- 入口脚本放在**项目根目录**（如 `./main.js`）
- 脚本里用**绝对路径**：`/sdcard/Download/项目名/res/...`
- 需要 `require` 其他模块时用正确层级：`../modules/xxx.js`

### 10.1 ⭐ `$log.i` / `$log.e` 只能传**一个**参数


### 10.2 ⭐⭐ `$root.getPermit()` 会把 root 通道**彻底搞死**

实测顺序：

```javascript
$root.exeRootShellSync("id");     // ✅ 正常，返回 uid=0(root)...
$root.getPermit();                // 它"返回"了，看着人畜无害
$root.exeRootShellSync("id");     // ❌ 永久不返回，脚本静默卡死
$root.exeRootShell("id", ...);    // ❌ 回调也不再触发
```

现象极难查：**没有报错、没有异常、AutoGOD 进程照常活着、日志就停在那一行**。

**正确做法**：只用 `hasPermit()` 查询，**绝不调 `getPermit()`**：

```javascript
if (typeof $root.hasPermit === "function" && $root.hasPermit()) { /* 可以用 root */ }
```

没权限就提示用户去界面上点授权，不要自己申请。

### 10.3 ⭐⭐⭐ `adb broadcast runJs` 启动的实例是"残废"的

本次最耗时的坑。同一份 `main.js`：

| 启动方式 | `exeRootShellSync` | `exeRootShell` 异步回调 |
|---|---|---|
| `adb ... runJs:./main.js` | ❌ `ui.show()` 之后永久卡死 | ❌ 从不触发 |
| 客户端打开 main.js → 点「运行」 | ✅ 正常 | ✅ 正常 |

**判断方法** —— 看日志有没有这两类行：

```
文件验证结果: true            ← lockcloud 的异步回调（正常实例才有）
获取到锁云状态: true
```

`runJs` 实例里这两行**都不会出现**。

**规矩**：
- 用 ADB 广播跑脚本，**只能验证纯逻辑**（字符串处理、文件读写、几何计算）
- **凡是涉及 root、或依赖回调的功能，必须用客户端「运行」按钮启动**再测
- 别因为 `runJs` 下 root 失灵就去改架构 —— 那是调试通道的问题，不是代码的问题

### 10.4 `$file.write(content, path)` —— **内容在前，路径在后**

```javascript
$file.write(fileContent, targetPath);   // ✅
$file.write(targetPath, fileContent);   // ❌
```

配套：`$file.read(path)`、`$file.exists(path)`（**不是 `exist`**）、`$file.mkdir(dir)`、`$file.del(path)`。

### 10.5 重复运行项目会堆叠界面 → 客户端崩溃卡死

**原因**：只 `$engine.stopAll()` / `$thread.stopAll()` **不会结束 Activity**，
`ui.show()` 出来的界面会一直留在栈里。实测连开 3 次，
`dumpsys activity activities | grep -c XActivity` 从 7 → 11 → 15（每次 +4 行）。

**两件事都要做**：

1. 「关闭」按钮里必须调 `ui.finish()`

```javascript
btnStop.click(() => {
    try { $floaty.closeAll(); } catch (e) {}
    try { ui.finish(); } catch (e) {}        // ← 关键，少了它就永远收不掉
    try { $thread.stopAll(); } catch (e) {}
    try { $engine.stopAll(); } catch (e) {}
});
```

2. **单实例守卫**：新实例把编号写进文件，旧实例定时自检、发现自己不是最新就自杀

```javascript
let _id = String(Date.now()) + "_" + Math.floor(Math.random() * 1000000);
let _p = "/sdcard/Download/项目名/_ui_owner.txt";
try { $file.write(_id, _p); } catch (e) {}
let t = setInterval(() => {
    let cur = $file.exists(_p) ? String($file.read(_p)).trim() : "";
    if (cur && cur !== _id) { clearInterval(t); try { ui.finish(); } catch (e) {} }
}, 2000);
```

实测：连开 4 次，XActivity 稳定在 7 不再增长，日志出现 3 次
「检测到有更新的实例启动了，本界面自动退出」。

### 10.6 排查"回调到底有没有执行"：回调里只改 JS 变量

别在后台线程的回调里写日志（可能不生效，会误判成"回调没执行"）。
改成只赋值 JS 变量，回主线程再打印：

```javascript
let flag = "none";
$root.exeRootShell("echo hi",
    function (l) { },
    function (e) { flag = "err:" + e; },
    function (c) { flag = "code:" + c; });
sleep(3000);
$log.i("结果=" + flag);     // 还是 none → 回调真的没执行
```

### 10.7 PowerShell 里自定义函数别叫 `R`

`R` 是 `Invoke-History` 的**内置别名**，而 **PowerShell 的别名优先级高于函数**，
自定义 `function R {}` 永远不会被调用，报错是「找不到命令行 xxx 的历史记录」。
取个不冲突的名字（例如 `RootSh`）。

### 10.8 只丢 TCP 的 UID 规则不会影响模拟器自身

`iptables -I OUTPUT 1 -m owner --uid-owner <游戏UID> -p tcp -j DROP`
实测：加规则前后模拟器 `ping` 表现完全一致（都是第 1 次冷启动 FAIL、之后 OK），
ADB 通信不受影响，`wlan0` 保持 `UP`。系统链 `bw_*` / `fw_*` / `oem_*` / `st_*` / `tetherctrl_*`
全部完好。规则插在 OUTPUT **第 1 条**，优先于系统链。

**绝对不要**用 `svc wifi disable`（模拟器的 wlan0 是虚拟网卡，关掉就再也连不回来）
或 `iptables -F`（会把安卓自带规则一起清掉）。

# 第十一章 调试通道与内存读写（2026-10 实测）

> 本章全部结论来自真机实测（雷电模拟器 Android 9 + AutoGOD），不是文档抄录。
> 官方文档里没写、但接的时候一定会踩的点都在这里。

## 11.1 ⚠️ `adb broadcast runJs` 启动的脚本实例是「残废」的

**这是本次排查耗时最久的一个坑，结论反直觉。**

| 场景 | `$root.exeRootShellSync`（同步） | `$root.exeRootShell`（异步） |
|------|-------------------------------|----------------------------|
| 纯脚本实例 + 没有项目 UI | ✅ 正常 | ❌ 回调不触发 |
| **`adb broadcast runJs` 启动的实例** | ❌ 已 `ui.show()` 后**永久卡死** | ❌ 回调不触发 |
| **客户端「运行」按钮启动的实例** | ✅ 正常 | ✅ 正常 |

实测证据（同一个脚本、同一台设备）：

- 广播实例：`$root.exeRootShellSync("id")` **永久不返回**，日志断在那一行，AutoGOD 进程还活着、无异常
- 客户端实例：`[弱网] 同步测试结果 = [uid=0(root) gid=0(root) ...]` ✅，`lockcloud` 的异步回调也正常 ✅

**推论：不要用广播实例去判断某个 API「能不能用」** —— 会得出完全错误的结论。
要复验 API 可用性，请走真机正常启动路径（客户端里点「运行」）。

> 另外：`runJs` 启动实例时如果反复不关界面，`XActivity` 会**堆积**（实测连开 4 次堆到 15 个）。
> 解决办法：`ui.finish()` + 单实例守卫（见 11.5）。

## 11.2 `$root.getPermit()` 会毒化整条 root 通道

**只查询权限用 `$root.hasPermit()`，绝对不要调 `$root.getPermit()`。**

实测：调用 `getPermit()` 之后，`$root.exeRootShellSync()` **永久卡死**、
`$root.exeRootShell()` **回调不再触发** —— 而 `getPermit()` 自己「返回」了，看不出任何异常。

正确做法：

```javascript
// ✅ 只查询，不申请
if (!$root.hasPermit()) {
    $log.e("没有 root 权限，请先在界面上点「Root」授权");
    return;
}
```

## 11.3 `$log.i` / `$log.e` 只接受一个参数

```javascript
// ❌ 错误：抛异常「找不到方法 …i(string, …)」，且整个函数静默中断
$log.i("弱网", "内容");
$log.e("设备信息", "读取失败");

// ✅ 正确：拼成一个字符串
$log.i("[弱网] 内容");
$log.e("[设备信息] 读取失败");
```

**为什么特别坑**：异常会在**按钮绑定函数内部**抛出，导致该函数**后面的所有绑定代码都不执行** ——
现象是「点了按钮完全没反应」，且日志里只有一行异常，很容易看漏。

## 11.5 重复运行会堆叠界面 → `ui.finish()` + 单实例守卫

**问题**：反复「运行」而不点「关闭」，AutoGOD 会不断新建 `XActivity`。
实测连开 3 次从 7 → 11 → 15 行（每次 +4），日志、点击事件都会串到旧实例上。

**两层修复**：

1. **`ui.finish()`** —— 主动关掉自己的界面（实测点「关闭」后 15 → 12）
2. **单实例守卫** —— 用「文件 + 时间戳编号」让新实例把旧实例踢下线：

```javascript
let _uiOwnerId = String(Date.now()) + "_" + String(Math.floor(Math.random() * 1000000));
let _uiOwnerPath = "/sdcard/Download/<项目名>/_ui_owner.txt";

// 写入自己的编号
function uiOwnerWrite() { try { $file.write(_uiOwnerId, _uiOwnerPath); } catch (e) { } }

// 定时检查：编号不是自己了，说明有更新的实例启动了
let uiOwnerTimer = setInterval(function () {
    try {
        if (!$file.exists(_uiOwnerPath)) return;
        let cur = String($file.read(_uiOwnerPath) || "").trim();
        if (cur && cur !== _uiOwnerId) {
            clearInterval(uiOwnerTimer);
            $log.i("[单实例] 检测到有更新的实例启动了，本界面自动退出");
            ui.finish();
        }
    } catch (e) { }
}, 2000);
```

实测：连开 4 次 `XActivity` 稳定在 7 不增长，3 次打出「检测到有更新的实例启动了」。

> ⚠️ `_ui_owner.txt` 是**运行时文件**，记得在 `.gitignore` 里加 `_*.txt`，别从设备同步回仓库。

## 11.6 验证回调是否执行：要在回调里「改 JS 变量」

**不要**在回调里打日志来判断 —— 日志通道本身也可能有问题，而且 `sleep` 会阻塞主线程让日志延迟。

正确做法（回调里改一个变量，回主线程读）：

```javascript
let flag = "none";
let lines = 0;
$root.exeRootShell("id",
    function (line) { lines++; },
    function () { },
    function () { flag = "done"; });
setTimeout(function () {
    $log.i("flag=" + flag + " lines=" + lines);   // flag=none lines=0 → 回调确实没执行
}, 3000);
```

## 11.7 ⭐ 局域网 WS（15431）是唯一能拿到 JS 返回值的通道

**广播是单向的、拿不到返回值。** 需要双向能力或返回值时走 WS。

**本机实测（2026-10，全部通过）**：

```
--> runJsCode:console.log('PROBE-MARKER');#_#_#/sdcard/Download/海岛助手
<-- log_v:[开始执行]
<-- log_i:PROBE-MARKER                    ← ① 代码真的执行了 ② console.log 会推到 WS
<-- log_v:[执行结束]: 海岛助手

--> runJsCode:setClip('PROBE-CLIP');#_#_#/sdcard/Download/海岛助手
--> getClip
<-- clipContent:PROBE-CLIP                ← ③ 取值回路成立！
```

| 前提 | 结果 |
|------|------|
| 该构建里 `runJsCode` 真的执行代码（不是演示占位） | ✅ 真的执行 |
| `console.log` 会转发到 WS 日志流 | ✅ 会，级别是 **`log_i:`** |
| 执行环境里 `setClip()` 可用 | ✅ Android 9 可用（**Android 12+ 需复验**） |

**取值回路（拿 JS 返回值的唯一实用办法）**：

```text
runJsCode:setClip(String(你的表达式));#_#_#<上下文路径>     →  无回包
getClip                                                     →  clipContent:<值>
```

其它实测要点：

- 端口**固定 15431**，**无鉴权**（明文 `ws://`）
- **没有请求 ID** → 需要关联回包的命令**不要并发**，且解析时要先跳过所有 `log_*` 帧
- `runJsCode` 的**真实格式是 `runJsCode:<代码>#_#_#<上下文路径>`**（不是文档里写的 `###`）
- `###` 是保留分隔符，路径里含 `###` 会让 `zip`/`unzip`/`rename` 全部错位
- `ls` 返回字段做 percent-encoding：`%`→`%25`、`#`→`%23`、`_`→`%5F`、`+`→`%2B`，**各解码一次**，别用会把 `+` 变空格的表单解码器
- **远程 WS** 有个路由陷阱：`RemoteWsClient` **不解析 `pc2phone#...#` 外层封装**，中继必须先把外层剥掉再转发，否则消息匹配不上任何命令

详见 `debug/adb-setup.md` 第九节与 `debug/ws.md` 附录。

## 11.8 `$mem` 内存读写库：三个官方点名的坑

`$mem` 全部方法**返回 JSON 字符串**，要先看 `ok` 字段：

```javascript
let r = JSON.parse($mem.info());
if (!r.ok) { $log.e("$mem 失败: " + r.error); return; }
```

| 坑 | 说明 |
|----|------|
| **地址字面量必须带 `L` 后缀** | `$mem.read(0x7f00001000L, 16)`；漏了后缀或写了十进制数会失败，**甚至搞崩目标进程** |
| **没连进程就读写** | 必须先 `$mem.init(pid)`；返回「尚未连接进程」就是这个原因 |
| **补丁/备份/ptrace 用完不恢复** | 会把目标进程卡住。`restorePatch` / `restoreBackup` / `trace(false)` **必须写在 `finally` 里** |

另外几个容易忽略的点：

- `createPatch` / `createBackup` 的**句柄存在底层 C++**，**进程被杀或重新 `init()` 都会失效**
- `remoteCall` / `remoteSyscall` **必须先 `trace(true)`**（`remoteCall` 最多 6 个参数）
- `watchMem` 的 threadId 是 **TID**（用 `lsThread()` 取），`timeoutMs` 上限 10000，且**依赖内核开放 perf 事件，部分设备用不了**
- `lsProc()` 在 Android 8.0 之后**读不到很多进程名** —— **看不到不代表进程不存在**
- `writeStr` 会自动补结尾 `\0`，目标要**预留多 1 字节**
- 无需 `init` 就能用的：`isSoLoad` / `getLoadError` / `info` / `selfTest` / `decodeArmCmd` / `checkPointer`

完整 API 见 `api/mem.md`。

## 11.9 实测「断网查雕像」的时间窗口

如果你在做断网相关的功能，这个数字很重要：

| 断网模式 | 游戏开始反应的时间 |
|---------|------------------|
| 只丢 TCP（`-p tcp -j DROP`） | **约 122 秒** → 游戏默默进「正在载入」重连界面 |
| TCP+UDP 全丢 | **约 120 秒** → 直接弹「连接中断 / 请检查您的网络连接并重试」 |

- **两种模式差别几乎没有**，用「只丢 TCP」即可（副作用更小）
- 90 秒内游戏完全正常可操作
- 这 **120 秒是游戏自己的应用层超时**，不是 TCP 层 —— 本机 `tcp_retries2 = 15`（≈805 秒）
  说明 TCP 层能撑很久，**改内核参数没用**
- 游戏只有 **1 条 TCP 连接**到服务器（TLS 443），所以**没法选择性放行心跳包**
  （同一条连接有队头阻塞，而且 TLS 加密看不到内容）
- 点「重试」但**不恢复网络** → 游戏卡死在「正在载入」，界面不可操作

## 十二、同步 vs 异步：`$root` 回调到底为什么不回来（2026-11 实测）

### 12.1 症状

日志只会看到自己的超时，命令其实早就执行成功了：

```
[声纳] root 超时: nsenter -t 1 -m am force-stop com.supercell.boombeach
```
但游戏确实被强停了 —— **命令跑了，只是回调没回来**。

### 12.2 先看结论表（健康实例、UI 已起来、同脚本 A/B 对照，2026-11 实测）

```
hasPermit = true
sync#1 用时  6ms -> uid=0(root) ...
sync#2 用时  8ms -> uid=0(root) ...
sync#3 用时 11ms -> uid=0(root) ...
async 已发出
async 1.5s 后 = line:uid=0(root) ...     ← 回调正常触发
async 4s   后 = exit=0 用时2006ms         ← 约 2 秒完成
async 之后 sync 再测 用时 2ms -> uid=0(root) ...   ← 互不干扰
```

**同步 6~11ms、异步约 2 秒，两者在这个实例里都正常。**
「`exeRootShellSync` 放 UI 线程必卡死」的旧结论**作废**（2026-10 那次卡死是 `getPermit()` 毒化通道导致的误归因）。

### 12.2b 实测：`sleep` 期间异步回调一次都不执行

```javascript
var flag = 'none';
$root.exeRootShell('id', l => flag = l, e => {}, c => flag = 'done');
sleep(3000);
// flag = none
sleep(5000);
// flag = none   ← 再等也没用
```

原因：`exeRootShell` 的回调靠 **JS 事件循环**送达，`sleep` 把线程占死，回调排不上队。

### 12.3 为什么「锁云 / 切换账号」用异步却是好的

它们都是**点一下按钮 → 发命令 → 立刻 return**，线程还给了事件循环，回调正常送达：

```javascript
// modules/lockcloud.js:238
$root.exeRootShell('nsenter -t 1 -m -- test -e "..."', () => {}, err => {}, exitCode => {
    ...   // ← 这个回调真的会执行
});
```
运行日志里 `[锁云] 文件验证结果: false` 就是**异步回调打出来的**，证明它工作正常。

**结论：不是异步坏了，是脚本不还手。**

### 12.4 选择规则

| 命令耗时 | 用什么 | 说明 |
|---|---|---|
| 毫秒级（`iptables`/`echo`/`cat`/`test`） | **同步 `exeRootShellSync()`** | 实测 4ms 返回，最简单可靠 |
| 1~5 秒（`am force-stop`/`pm`/`cp` 小文件） | 同步也可以 | 接受这段时间线程被占 |
| >5 秒（解压/大拷贝） | **异步 + 超时兜底，且全程不 `sleep`** | 用 `setTimeout` 串联 |

### 12.5 三条配套红线

1. **不要为了"保险"把短命令写成异步** —— 在长流程里反而收不到回调。
2. **要异步就整条流程事件驱动**，绝不在等待期间 `sleep` / 跑大循环。
3. **别用 `getPermit()`**，它会毒化整条 root 通道；只判断权限用 `hasPermit()`。

## 十三、模拟器开关 WiFi 做「秒级断网」（2026-11 三次实测，结论：可用，但必须成对下发）

> 一句话：**`svc wifi disable` 绝对不能在电脑端单独执行；必须把「关」和「自己开」写在同一行、由设备端后台执行。**
>
> 这是目前**唯一能让游戏秒级弹「连接中断」**的手段（约 4 秒），比 iptables 方案快一个数量级。

### 13.1 为什么它能秒弹：内核当场拆 socket

| 手段 | 游戏多久发现断网 | 机制 |
| --- | --- | --- |
| `iptables -j DROP` | 约 **120 秒** | 包被静默丢弃，游戏只能等自己的心跳超时 |
| `iptables -j REJECT --reject-with tcp-reset` | 约 **57 秒** | 包被拒，但游戏也要等下一次发包才发现 |
| `ip route add unreachable <IP>` | 约等于 REJECT | 同上（发包才报错） |
| `tc qdisc ... loss 100%` | 约 120 秒 | 等同 DROP |
| **`svc wifi disable`（接口 down）** | **约 4 秒** | **接口一 down，内核立刻把该接口上的 TCP socket 全部拆掉，游戏当场收到错误** |

**结论**：想「秒」，靠的不是「包发不出去」，而是**把那条 TCP 连接拆掉**。
Android 9 的 toybox **没有 `ss`**（实测 `ss: not found`），也没有 `conntrack`，
所以 `ss -K dst <IP>` 这种「只杀单条连接」的办法用不了。
**接口 down/up 是唯一可用的秒杀手段，而 `svc wifi` 就是它最直接的开关。**

### 13.2 事故：从电脑端单独关 WiFi，设备当场失联且无法救回

```
adb shell su -c 'svc wifi disable'      # ← 错误：只关，没有开
-> error: device 'emulator-5554' not found
-> 之后再也发不出 enable
```

**根因**：雷电模拟器只有 `lo` + `wlan0` 两个网络接口，**adb 走的也是 wlan0**。
关掉 wlan0 等于把调试通道一起关掉，主机侧从此没有任何手段把网络打开
（有权限发命令的进程已经联系不上了）。

**后果**：模拟器实例直接跑崩，只能让用户重开一个实例。

**救回方式**（能试就试）：`dnconsole reboot --index 0`，**必须管理员权限**，
否则报 `os error 740: 请求的操作需要提升`。实测重启后约 105 秒设备才重新上线。

### 13.3 正确姿势：成对下发，由设备自己执行（三次实测全成功）

```bash
adb shell su -c 'nohup sh -c "svc wifi disable; sleep 4; svc wifi enable" >/dev/null 2>&1 &'
```

关键点：
- `nohup ... &` 让脚本在**设备本地后台**跑 —— adb 断了它也照常执行下去，这是整件事的安全底座；
- 4 秒后 WiFi 自己回来，IP 恢复，adb 自动重连。

AutoGOD 脚本里的等价写法（同步 root）：

```javascript
$root.exeRootShellSync("su -c \"nohup sh -c 'svc wifi disable; sleep 4; svc wifi enable' >/dev/null 2>&1 &\"");
```

**三次实测记录**：

| 次数 | 场景 | 结果 |
| --- | --- | --- |
| 1 | 干跑，测弹窗速度 | 4 秒 WiFi 断 → 游戏秒弹「连接中断」；WiFi 自愈；点「重试」后 1.8 秒弹窗消失、8.4 秒回主基地 |
| 2 | 带 DROP 规则时丢弃一发 | 整条链路 25 秒，炮弹 54→54 **零消耗**，iptables 零残留 |
| 3 | 全新实例上复测 | **3 秒断、6 秒自愈，adb 全程没断** |

所以：**开关 WiFi 本身完全可用，崩实例是「只关不开」导致的，不是反复开关导致的。**

### 13.4 顺序不能错：先删断网规则，再点「重试」

正确顺序（实测零消耗）：

1. 保持 DROP 规则（游戏处于断网）
2. 设备端 WiFi 关 4 秒再开 → 游戏弹「连接中断」
3. **先删掉 DROP 规则**（`while iptables -D ... do :; done`）
4. 再点「重试」（弹窗里的按钮，1280×720 下约在 `(347, 427)`）
5. 游戏自己重载回主基地 → 核对炮弹数没变

**为什么必须先删规则**：点「重试」时游戏要重新连服务器，DROP 还在就会立刻再弹一次，陷入死循环。

**为什么这一发不会漏**：WiFi 断开时 TCP 连接已被内核拆掉，重载是从服务器重新拉状态，挂起请求不会补交。

### 13.5 三重保险写法（照抄）

```javascript
// ① 关和开必须在同一行、设备端后台执行
$root.exeRootShellSync("su -c \"nohup sh -c 'svc wifi disable; sleep 4; svc wifi enable' >/dev/null 2>&1 &\"");

// ② 等待 + 兜底再开一次（防止 disable 卡住迟迟不返回）
sleep(16000);
$root.exeRootShellSync("su -c 'svc wifi enable'");
sleep(1500);
$root.exeRootShellSync("su -c 'ip link set wlan0 up' 2>/dev/null || true");

// ③ 脚本任何出口（正常结束 / 异常 / 用户点关闭）都要执行
try {
  $root.exeRootShellSync("su -c 'svc wifi enable'");
  $root.exeRootShellSync("su -c 'while iptables -D OUTPUT -m owner --uid-owner " + UID + " -p tcp -j DROP 2>/dev/null; do :; done'");
} catch (e) { /* 出口兜底失败也要吞掉，不能让异常盖住原错误 */ }
```

### 13.6 反复开关可能把模拟器搞死时的诊断三连

即使写法正确，模拟器也可能因为别的原因崩。出现 `adb devices` 空但端口还在时，按顺序查：

1. **看内存**：`Get-Process Ld9BoxHeadless,dnplayer | Select ProcessName,@{n='MB';e={[int]($_.WorkingSet64/1MB)}}`
   —— 只有几百 MB 就是**安卓虚拟机没起来**（正常应 1~3 GB）
2. **看握手**：5555 端口连得上但 `no banner (n=-1)` → adbd 根本没应答（不是「未授权」，未授权会回 `unauthorized`）
3. **重启实例**：`dnconsole quit --index 0` 再 `dnconsole launch --index 0`，**必须管理员权限**

### 13.7 附带坑：AutoGod Studio 自带的 adb 会抢 5037 端口

路径：`C:\Users\admin\AutoGod\adb\win32\platform-tools\adb.exe`

它会和系统 adb（如 `H:\adb\adb.exe` 37.0.0）**抢同一个 5037 端口**，
表现为 `adb devices` 看到过期的 `offline` 条目、`adb connect` 反复失败。

排查：
```powershell
Get-NetTCPConnection -LocalPort 5037 -State Listen | Select OwningProcess
Get-Process -Id <pid> | Select Path
```
临时规避：给系统 adb 换端口 `adb -P 5038 start-server`。
`taskkill /F /IM adb.exe` 没用 —— IDE 会立刻把它拉起来。

### 13.8 两个必须动态解析、绝不能写死的值

换实例 / 重装游戏后这两个值都会变（实测 UID 从 `10065` 变成 `10056`，IP 从 `192.168.0.21` 变成 `192.168.0.26`）：

```bash
# 游戏 UID
adb shell su -c "dumpsys package <包名> | grep -m1 userId="

# 设备当前 IP（WS 调试也靠它）
adb shell "ip -4 addr show wlan0 | grep inet"

# 游戏当前连的服务器（/proc/net/tcp 第 8 列是 uid）
adb shell su -c "cat /proc/net/tcp"
```

> `/proc/net/tcp` 里的地址和端口是**小端十六进制**：`2275E10D` = `13.225.117.34`，`:01BB` = `443`。

### 13.9 结论（给自动化脚本的规则）

- ✅ 允许：**设备端成对下发** `svc wifi disable; sleep N; svc wifi enable`
- ❌ 禁止：电脑端单独 `svc wifi disable`（会连 adb 一起关，实例报废）
- ❌ 禁止：`iptables -F`（会清掉安卓自带的 `bw_*` / `fw_*` 链）
- ✅ 断网优先用 `iptables -I OUTPUT 1 -m owner --uid-owner <游戏UID> -p tcp -j DROP`（慢但绝对安全）
- ✅ 要「秒」才用 WiFi 开关，并且只在**设备端脚本**里用（不依赖 adb）
