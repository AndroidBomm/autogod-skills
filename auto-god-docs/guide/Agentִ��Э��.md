## 一、线程模型铁律

**主线程就是 UI 线程。** AutoGOD 的脚本入口（`main.js`）如果已经调用了 `ui.show()`（或已用 `$floaty.newApp()` / `$floaty.newAdj()` 建好悬浮窗），那么**它所在的线程就是 UI 线程** —— 在这条线程上做任何耗时操作，界面都会**直接卡死**（不是变慢，是整块界面变灰、点不动、系统弹「无响应」）。

### 三条铁律

| 铁律 | 说明 |
|------|------|
| **① 同步阻塞 API 绝不放 UI 线程** | 凡是「调用后要等到命令在设备上执行完才返回」的方法，都必须挪到独立线程或独立脚本实例。 |
| **② 回调里不要同步等待** | 异步 API 的回调本身就在别的线程上；在回调里再调同步 API、或用忙等循环等一个标志位，等于把那条线程也堵死。 |
| **③ 长任务一律 `setTimeout` / 独立实例** | 循环、等图、扫码、批量上号这类活儿，用 `setTimeout` 分片，或交给独立脚本实例。**不要在 UI 线程 `sleep`。** |

### 已实测的典型案例（本项目踩过，血泪）

> **`$root.exeRootShellSync()` 在已经 `ui.show()` 的实例里调用，会「永久不返回」** —— 界面直接死，日志停在那一行，没有异常、没有超时，进程还活着。同场景下异步的 `$root.exeRootShell()` 回调**也不会触发**。
>
> **结论**：`exeRootShellSync` 这类同步 shell 方法，要么放在**还没显示界面的早期初始化**里，要么交给**独立脚本实例**（`$engine.run()`）。绝对不要放在按钮点击回调里。

### 正确 / 错误对照

```javascript
// ❌ 错误：按钮回调里直接调同步 shell —— 界面会永久卡死
btn.click(function () {
    let out = $root.exeRootShellSync("id");
    $log.i("结果: " + out);
});

// ✅ 正确：用异步 + 超时兜底，界面全程不卡
btn.click(function () {
    let done = false;
    let tid = setTimeout(function () {
        if (!done) { $log.e("超时：命令 5 秒未返回"); }
    }, 5000);
    $root.exeRootShell("id", function (out) {
        done = true;
        clearTimeout(tid);
        $log.i("结果: " + out);
    });
});
```

```javascript
// ❌ 错误：在 UI 线程 sleep 等图
while (true) {
    if ($ag.findImg({ path: "/sdcard/ready.png" })) break;
    sleep(1000);              // 界面全程卡死
}

// ✅ 正确：setTimeout 分片轮询，界面保持响应
function waitReady(retry) {
    retry = retry || 0;
    if (retry > 60) { $log.e("等图超时"); return; }
    if ($ag.findImg({ path: "/sdcard/ready.png" })) { nextStep(); return; }
    setTimeout(function () { waitReady(retry + 1); }, 1000);
}
```

## 三、常见低级错误清单（AI 必查）

写完之后**逐条核对**。分三级：致命错误（直接失败）、逻辑错误（能跑但行为不对）、细节坑（老手也会踩）。

### 3.1 致命错误（编译/运行直接失败）

1. **XML 根节点写成 `<LinearLayout>`** —— AutoGOD XML 标签**全小写**，根节点是 `<ui>`，属性用缩写（`w`/`h`/`bg`/`dir`）。
2. **`ui.id()` 拿到的控件为 null 就直接调方法** —— 必须判空，否则整段脚本中断。
3. **图标名凭感觉猜** —— 内置图标名不存在会**静默不显示、不报错**。先查 `ui/icon-list.md`（1537 个），命名规律是 `<名字>_fill` / `<名字>_outline`，**没有裸名**。
4. **`$root.getPermit()` 在 UI 线程调用** —— 会毒化 root 通道（见 3.3）。
5. **同步 shell 放 UI 线程** —— 见第一节铁律。
6. **`require()` 路径写错 / 模块没导出** —— 模块化项目里最常见的一次性错误。
7. **权限没申请就调用对应 API** —— 权限优先级是 **ROOT > Shizuku > Accessibility**，`$permit` 的方法只调一次（内部缓存）。
8. **`$ui` 的 `ui.show()` 之后还改控件初始值** —— 界面已经构建完了，改了不生效。

### 3.2 逻辑错误（能运行但行为不对）

1. **坐标写死** —— 换设备、换分辨率即失效。**控件优先于坐标**：能用节点/图色就不要用固定坐标。
2. **点了「僵尸节点」** —— 节点还在树里但用户看不见。用选择器提前筛掉：`$act.selector().visible(true)`。注意 `visible` 是节点的**只读属性**（`node.visible`，且**没有** `getVisible()`），**不是方法**，写成 `visibleToUser(true)` 会直接报错。
3. **`clickable` 判断错层** —— `clickable` 常常在文本的**父容器**上，要向上找（最多 8 层）。
4. **等图/等节点没有超时** —— 无限等待 = 脚本挂死。
5. **成功信号不明确** —— 「点了按钮」不等于「操作成功」，必须定义可判定的成功信号（界面出现某元素 / 文件内容变化 / 日志出现某关键字）。
6. **失败没处理** —— 每一步都要有失败分支，不能只写 happy path。
7. **动作太快** —— 连续点击之间没有延迟，或者延迟固定不变。**加随机延迟**（模拟人类），降低风控命中。
8. **状态没持久化** —— 多账号/长任务没记进度，中断后从零开始。用 `$storage` 记录断点。
9. **`open()` 用完不 `close()`** —— 文件/数据库句柄泄漏。
10. **监听器/定时器没注销** —— 界面关了还在跑。

### 3.3 细节坑（本轮真机实测新增）

| 坑 | 现象 | 正确做法 |
|----|------|----------|
| **`$log.i()` / `$log.e()` 只接受一个参数** | 传两个参数会抛「找不到方法」，而且**整个绑定函数静默中断**（本项目实测：按钮绑定整段没执行，只在日志里看到异常） | 拼接成一个字符串：`$log.i("弱网: " + msg)` |
| **`$root.getPermit()` 会毒化 root 通道** | 调用之后，所有 `exeRootShell*` **永久不返回**（本项目实测踩了几个小时） | 只查状态用 `$root.hasPermit()`；没权限就提示用户去授权，**绝不主动调 `getPermit()`** |
| **`$file.write(content, path)` 参数顺序** | **内容在前、路径在后**。写反不报错，静默写到错的地方 | `$file.write("内容", "/sdcard/x.txt")` |
| **`$file.exists` 不是 `exist`** | 名字记错会抛异常 | `$file.exists(path)` |
| **重复运行堆叠界面** | `ui.finish()` 只在用户点「关闭」时有效，直接再运行会一层层叠加 | 自己写单实例守卫（状态文件 + 定时检测编号） |
| **`toast` / `log` / `console` 不是一回事** | 调试时用错通道，看不到输出 | 需要持久化查证用 `$log`（写日志文件）；瞬时提示用 `toast` |
| **排查「回调到底有没有执行」** | 在回调里写日志会掩盖问题（日志通道本身可能没起来） | 回调里**只改一个 JS 变量**，再回主线程读它 |
| **调试用的实例可能「残废」** | `adb broadcast runJs` 启动的实例与用户点「运行」启动的实例行为**可能不同**（本项目实测：广播实例的异步回调不触发、同步 shell 死锁） | **不要用广播实例判断某个 API 能不能用**，要用真机正常启动路径复验 |

## 四、修复内环：三步，且禁止无修改重试

出错时的固定动作，**顺序不能变**：

1. **日志定位** —— 拿到**真实错误原文**（不是猜测）。没有报错就去加日志、加探针，直到拿到原文。
2. **写出被修改的假设/参数** —— 用一句话说清「我认为原因是 X，所以我要改 Y」。**写不出来就不许重试。**
3. **回到生成** —— 改完再跑，回到第 1 步。

### 禁止连续无修改重试

**同一个错误连续出现两次，第三次尝试之前必须能说清楚「这次和上次有什么不同」。**

- ❌ 「再跑一次看看」 —— 没有修改的重试
- ❌ 「可能是偶发问题，重启一下」 —— 没有假设的猜测
- ✅ 「上次超时是因为命令里单引号被设备 sh 提前闭合（`syntax error: unexpected '('`），这次我把单引号改成了 `'\''` 转义」

### 工具误报条款（可判定）

以下情况**不算命令失败**，不要误判：

| 现象 | 判定 |
|------|------|
| `am broadcast` 输出 `Broadcast completed: result=0` | **不代表脚本执行成功** —— 广播是单向的，没有回执。要验证脚本真的跑了，用「脚本写文件 → `adb shell cat` 读回」 |
| `adb shell ping` 第一次 FAIL、后面 OK | 模拟器/设备的 ICMP 预热现象，**不是网络不通**。连续测 3 次再判断 |
| `dumpsys` 里某个字段为空 | 可能是该 Android 版本不暴露，**不等于功能异常** |

### 迭代上限

**由用户决定**。不要自己设定「我再试 5 次就放弃」，也不要在没告知的情况下无限循环。连续 3 轮没有进展就停下来汇报当前卡点和已排除的可能。

## 五、交付六段式

每次交付必须包含这六段，**其中【验证】和【限制】不许省略**：

```
1. 【做了什么】   —— 一句话说明改动范围（哪个文件、哪个功能）
2. 【怎么用】     —— 用户需要怎么操作（点哪里、传什么参数）
3. 【验证】       —— 真实证据：日志原文 / 截图 / 文件内容对比。禁止「应该可以」
4. 【限制】       —— 明确写出这件事做不到什么、什么条件下会失败
5. 【回滚方式】   —— 出问题怎么恢复（改哪个文件、撤哪个提交）
6. 【下一步建议】 —— 可选项，以及各自的风险
```

## 六、失败禁止粉饰

失败就写失败。**只报三样东西**：

1. **失败在哪一步**
2. **真实错误原文**（贴日志，不要转述）
3. **下一步建议**

禁止出现的表述：「基本可用」「应该没问题」「大概可以了」「功能已实现（未测试）」。

## 七、观测与定位优先级阶梯

排查「界面上有什么」时，**从上往下试，不要跳级**：

1. **结构化节点树**（`$act.selector()` / `dumpNodeInfo`）—— 最快、最准、最省
2. **图色识别**（`$ag` / `$color`）—— 节点树拿不到时的主力
3. **OCR**（`$ocr`）—— 文本是图片/自绘时
4. **截图 + 人眼看** —— 兜底（也最慢）

> **节点树缺节点时不要反复猜选择器** —— 那说明该控件是自绘或不在无障碍树里，直接升级到图色方案。反复改选择器是典型的无效重试。

## 八、长任务记忆（AutoGOD 项目最缺的一环）

跑多阶段的长任务（多账号、批量上号、长时间挂机）时：

1. **开工先回读进度文件** —— 如果存在 `/sdcard/<项目>/_progress.txt`，从里面记录的断点继续，**不要从零开始**。
2. **每完成一个阶段追加一行** —— 格式 `阶段名|时间戳|结果`。
3. **中断后按进度续接** —— 重启脚本时先看进度文件，跳过已完成的阶段。
4. **任务结束后删除进度文件**（或归档）。

```javascript
const PROG = "/sdcard/MyProject/_progress.txt";

function markStage(stage, result) {
    let line = stage + "|" + $date.format("yyyy-MM-dd HH:mm:ss") + "|" + result + "\n";
    let old = $file.exists(PROG) ? $file.read(PROG) : "";
    $file.write(old + line, PROG);
}

function lastStage() {
    if (!$file.exists(PROG)) return "";
    let lines = $file.read(PROG).split("\n");
    for (let i = lines.length - 1; i >= 0; i--) {
        if (lines[i].indexOf("|") > 0) return lines[i].split("|")[0];
    }
    return "";
}
```

## 十、用户任务下达模板（给用户看）

想让 AI 少走弯路，按这个格式描述任务：

```
【目标】把「XXX」自动化，现在手动需要 N 步
【环境】设备型号 / Android 版本 / 目标 APP 版本
【现状】我已经试过 XXX，卡在 XXX（附日志或截图）
【成功标准】出现 XXX 就算成功
【限制】不能做 XXX（例如不能改游戏文件、不能用 root）
```

**如果缺少【成功标准】，AI 必须先问清楚再动手** —— 没有成功标准的自动化任务，写完也无法验证。
